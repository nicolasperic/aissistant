## 1. Configuration File Architecture

Magento 2 splits its configuration across multiple files and storage layers. Understanding *why* each file exists is more important on the architect exam than memorising syntax.

### 1.1 The Two Critical PHP Config Files

```
app/
  etc/
    config.php        <-- COMMITTED to VCS
    env.php           <-- NEVER committed to VCS
```

| File | Purpose | Committed? | Editable via Admin UI? |
|---|---|---|---|
| `config.php` | Shared system config, module enable/disable list, store config snapshot | **Yes** | No — locked after dump |
| `env.php` | Environment-specific: DB, cache, session, crypt key | **No** | No — CLI or direct file edit only |

### 1.2 config.php — Structure

Generated by `bin/magento app:config:dump`. Contains:

```php
<?php
return [
    'modules' => [
        'Magento_Store' => 1,
        'Magento_Directory' => 1,
        // ... all enabled modules
    ],
    'system' => [
        'default' => [
            'general' => [
                'locale' => ['code' => 'en_US'],
            ],
        ],
    ],
    'scopes' => [ /* website/store view definitions */ ],
    'themes' => [ /* active theme definitions */ ],
];
```

> **Exam focus:** `config.php` stores the **module list** AND optionally the **system configuration** (store settings). The module list is always written; the system config is only written when you explicitly dump it.

### 1.3 env.php — Structure

Created by the Magento installer or manually. Never generated by `app:config:dump`.

```php
<?php
return [
    'backend' => ['frontName' => 'admin'],
    'crypt' => ['key' => 'your-encryption-key'],
    'db' => [
        'table_prefix' => '',
        'connection' => [
            'default' => [
                'host' => 'localhost',
                'dbname' => 'magento2',
                'username' => 'magento',
                'password' => 'secret',   // SENSITIVE — never commit
                'active' => '1',
            ],
        ],
    ],
    'resource' => ['default_setup' => ['connection' => 'default']],
    'x-frame-options' => 'SAMEORIGIN',
    'MAGE_MODE' => 'developer',
    'session' => ['save' => 'files'],
    'cache' => [
        'frontend' => [
            'default' => ['backend' => 'Cm_Cache_Backend_Redis', ...],
            'page_cache' => ['backend' => 'Cm_Cache_Backend_Redis', ...],
        ],
    ],
    'lock' => ['provider' => 'db'],
    'cache_types' => [ /* cache type on/off flags */ ],
    'directories' => ['document_root_is_pub' => true],
];
```

> **Exam focus:** `env.php` is the **only** place for credentials, encryption keys, and environment-specific infrastructure config (Redis, DB). If a question asks where DB credentials live — **env.php, not config.php, not the database**.

## 2. The Configuration Hierarchy

This is one of the most tested architectural concepts. Three layers, each overriding the one before it.

```
Layer 1 (Lowest priority)         Layer 2                    Layer 3 (Highest priority)
+---------------------------+    +---------------------+    +---------------------------+
|  config.xml / config.php  | -> |  core_config_data   | -> |  Environment Variables    |
|  (default/module values)  |    |  (DB, Admin UI)     |    |  (env.php / shell env)    |
+---------------------------+    +---------------------+    +---------------------------+
       "What ships"                "What admin set"           "What ops team controls"
```

### 2.1 Layer 1 — Default Configuration (config.xml)

Every module declares its default config values in `etc/config.xml`:

```xml
<!-- Vendor/Module/etc/config.xml -->
<config xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
        xsi:noNamespaceSchemaLocation="urn:magento:module:Magento_Store:etc/config.xsd">
    <default>
        <catalog>
            <frontend>
                <list_per_page>12</list_per_page>
            </frontend>
        </catalog>
    </default>
</config>
```

> **Exam focus:** `config.xml` values are the **fallback** — they apply when no Admin UI setting or env var override exists. Changing `config.xml` requires a code deployment, not just cache flush.

### 2.2 Layer 2 — Database Configuration (core_config_data)

Values saved in Admin UI → Stores → Configuration land in the `core_config_data` table.

```sql
SELECT scope, scope_id, path, value
FROM core_config_data
WHERE path = 'catalog/frontend/list_per_page';
```

| scope | scope_id | path | value |
|---|---|---|---|
| default | 0 | catalog/frontend/list_per_page | 24 |
| websites | 1 | catalog/frontend/list_per_page | 12 |

Scope hierarchy (most specific wins): `store` > `websites` > `default`

### 2.3 Layer 3 — Environment Variable Overrides

Environment variables in the format `CONFIG__<SCOPE>__<PATH_WITH_DOUBLE_UNDERSCORE>` **always win**, regardless of what the Admin UI shows.

```bash
# Format: CONFIG__<SCOPE_TYPE>__<SCOPE_CODE?>__<PATH>
# Default scope:
CONFIG__DEFAULT__CATALOG__FRONTEND__LIST_PER_PAGE=48

# Website scope (scope_id = 1, but use website code):
CONFIG__WEBSITES__BASE__CATALOG__FRONTEND__LIST_PER_PAGE=36
```

Set in `env.php` under the `system` key, or as actual OS environment variables:

```php
// env.php — env var style overrides
'system' => [
    'default' => [
        'catalog' => [
            'frontend' => [
                'list_per_page' => 48,
            ],
        ],
    ],
],
```

> **Exam focus (Critical):** After running `app:config:dump`, Admin UI fields that were dumped become **locked/greyed out**. The only ways to change them are:
> 1. Edit `config.php` directly and redeploy
> 2. Set an environment variable override
> 3. Delete the value from `config.php` (restores Admin UI editability)
>
> This is an architectural *intentional* feature — it enforces that production config is version-controlled.

### 2.4 Sensitive vs. Environment-Specific Config

| Type | Storage | Example |
|---|---|---|
| **Sensitive** | Environment variables / `env.php` ONLY | API keys, passwords, payment credentials |
| **Environment-specific** | `env.php` | DB host, Redis host, base URL |
| **System / Shared** | `config.php` (committed) | Tax classes, catalog settings, CMS blocks |

```bash
# Mark a config path as sensitive — writes to env.php, prevents it from being dumped to config.php
bin/magento config:sensitive:set payment/braintree/private_key "actual-key"
```

> **Exam focus:** Sensitive configuration paths are declared via `di.xml` by injecting into `Magento\Config\Model\Config\TypePool` — there is no `config_sensitive.xml` file type. Modules register sensitive paths by passing an array of `path => "1"` items to the `sensitive` constructor argument of `TypePool` via `di.xml`. This prevents those paths from being written to `config.php` during `app:config:dump`. A question about PCI compliance or credential handling should immediately point you toward env vars and TypePool-declared sensitive paths.

Example (from `module-paypal/etc/di.xml`):
```xml
<type name="Magento\Config\Model\Config\TypePool">
    <arguments>
        <argument name="sensitive" xsi:type="array">
            <item name="payment/payflowpro/pwd" xsi:type="string">1</item>
            <item name="payment/payflowpro/user" xsi:type="string">1</item>
            <!-- ... -->
        </argument>
    </arguments>
</type>
```

## 3. app:config:dump — Deep Dive

### 3.1 What It Does

```bash
bin/magento app:config:dump
```

Writes the following to `config.php`:
- **Module list** — always included
- **System configuration** — store config values from `core_config_data`
- **Scopes** — website and store view definitions
- **Themes** — active theme assignments

### 3.2 What It Does NOT Do

- Does **not** write to `env.php`
- Does **not** export sensitive config (those are filtered out by TypePool)
- Does **not** export `core_config_data` values marked as environment-specific

### 3.3 The Lock-Down Effect (Architecturally Critical)

```
Before app:config:dump:               After app:config:dump:
+------------------------+            +------------------------+
| Admin UI               |            | Admin UI               |
| [Catalog] Per Page: 24 |            | [Catalog] Per Page: 24 |
| [EDITABLE FIELD]       |            | [GREYED OUT / LOCKED]  |
+------------------------+            +------------------------+
        |                                       |
        v                                       v
  core_config_data                      config.php (authoritative)
  (authoritative)                       core_config_data (ignored for
                                        paths present in config.php)
```

**Why this exists architecturally:**
The intent is to make store configuration **reproducible across environments**. If a value is in `config.php` and committed to VCS, every environment gets identical configuration — no manual Admin UI changes that can drift between staging and production.

> **Exam focus:** The question "why is the Admin UI field locked after config:dump?" has a deeper answer than "it was dumped." The *architectural reason* is to enforce environment parity and prevent configuration drift between staging and production. This is the answer an architect is expected to give.

### 3.4 Selective Dumping

```bash
# Dump only specific config types
bin/magento app:config:dump scopes     # Only website/store scopes
bin/magento app:config:dump system     # Only system config
bin/magento app:config:dump themes     # Only theme assignments
bin/magento app:config:dump i18n       # Only translations
```

## 4. Environment Variables as Configuration Overrides

### 4.1 Naming Convention

```
CONFIG__<SCOPE>__<PATH_SEGMENTS_DOUBLE_UNDERSCORE>

SCOPE values:
  DEFAULT          → applies to default scope
  WEBSITES__<code> → applies to a specific website
  STORES__<code>   → applies to a specific store view
```

```bash
# Examples:
CONFIG__DEFAULT__WEB__UNSECURE__BASE_URL=https://staging.example.com
CONFIG__DEFAULT__GENERAL__LOCALE__CODE=en_US
CONFIG__WEBSITES__US__WEB__UNSECURE__BASE_URL=https://us.example.com
```

### 4.2 Adobe Commerce Cloud — Specific Env Vars

On Magento Cloud, environment variables are set via `.magento.env.yaml` or the Cloud console:

```yaml
# .magento.env.yaml (cloud-specific, NOT for app config override)
stage:
  global:
    SKIP_HTML_MINIFICATION: false
  deploy:
    CACHE_CONFIGURATION:
      _merge: true
      frontend:
        default:
          backend: Cm_Cache_Backend_Redis
```

> **Exam focus:** Cloud environment variables set in the Cloud console or `.magento.env.yaml` under the `MAGENTO_CLOUD_VARIABLES` key are different from the `CONFIG__*` pattern. Know which mechanism serves which purpose.

## 5. Application Modes

### 5.1 Mode Comparison Table

| Feature | `developer` | `production` | `default` |
|---|---|---|---|
| Error display | Full stack trace in browser | Suppressed (logged only) | Suppressed |
| Exception page | Detailed | Generic "We apologize" | Generic |
| Static assets | Generated on-the-fly per request | Must be pre-deployed | Generated on-the-fly |
| DI compilation | Regenerated on every request | Must be pre-compiled | Skipped |
| Symlinks for static | Yes (pub/static symlinks to source) | No (actual files copied) | No |
| Template hints | Available | Not available | Not available |
| Performance | Slow (not for prod) | Optimised | Mediocre |
| `generated/` rebuild | Automatic | Manual (`di:compile`) | Manual |

### 5.2 Switching Modes

```bash
# Check current mode
bin/magento deploy:mode:show

# Switch to developer (development environments only)
bin/magento deploy:mode:set developer

# Switch to production (triggers static content deploy + DI compile)
bin/magento deploy:mode:set production
```

### 5.3 The White Screen of Death — Mode Dependency

In **production mode**, PHP errors are suppressed. A fatal error = white screen. In **developer mode**, a fatal error shows the full stack trace.

```
Production Mode PHP Fatal Error:
+----------------------------------+
| We apologize for this inconven-  |
| ience. Please try again later.   |
+----------------------------------+
     (No stack trace visible)
     ERROR IS IN: var/log/exception.log

Developer Mode PHP Fatal Error:
+----------------------------------+
| Fatal error: Uncaught Exception  |
| Stack trace:                     |
| #0 ...Plugin.php(45): ...        |
| #1 ...                           |
+----------------------------------+
     (Full trace visible in browser)
```

> **Exam focus (Critical):** When diagnosing a white screen of death in production:
> **FIRST step = check `var/log/exception.log`**
> NOT clearing cache. NOT running di:compile. NOT switching modes.
> The exam specifically tests this ordering. Clearing cache before reading logs can destroy evidence.

## 6. Log Files — What Each Contains

### 6.1 Log File Reference Table

| File | Location | Contains | When to Check |
|---|---|---|---|
| `system.log` | `var/log/system.log` | General application notices, warnings — deprecations, non-critical errors, module info messages | Unexpected behaviour, module issues |
| `exception.log` | `var/log/exception.log` | **All uncaught exceptions** with full stack trace | White screen, 500 errors — **check FIRST** |
| `debug.log` | `var/log/debug.log` | Verbose debug output (only active in developer mode or when explicitly enabled) | Deep debugging — **disable in production** |
| `cloud.log` | `var/log/cloud.log` | Adobe Commerce Cloud platform events — hook execution, environment provisioning | Cloud deploy failures |
| `deploy.log` | `var/log/deploy.log` | Magento deploy-phase output — config import, DI compile, SCD results | Deployment failures |
| `report/` | `var/report/<id>` | Full exception reports linked from the error page (each error gets a unique ID) | When the error page shows a report number |

### 6.2 Reading exception.log

```
[2024-04-30 10:15:32] main.CRITICAL:
  Plugin class Vendor\Module\Plugin\ProductPlugin
  does not implement interface method afterGetName
  correctly — return type must be ?string, bool returned
  {"exception":"[object] (TypeError ...)"} []
```

Structure: `[timestamp] logger_name.LEVEL: message {"context"} []`

### 6.3 Enabling/Disabling debug.log

`dev/debug/debug_logging` is a **deployment config** path stored in `env.php`. It is set automatically when switching application modes, or via:

```bash
# Via setup:config:set (writes to env.php — correct command for deployment config)
bin/magento setup:config:set --enable-debug-logging=1   # Enable
bin/magento setup:config:set --enable-debug-logging=0   # Disable (MUST be 0 in production)
```

The path constant `CONFIG_PATH_DEBUG_LOGGING = 'dev/debug/debug_logging'` is defined in `Magento\Config\Model\Config\Setup\ConfigOptionsList`. Switching to production mode (`deploy:mode:set production`) automatically sets it to `0`.

> **Exam focus:** `debug.log` being enabled in production is a **security and performance risk** — it can expose sensitive data and fill disk space. The exam may present a scenario where performance degrades in production; enabling debug logging is a likely culprit.

### 6.4 Log Level Hierarchy

```
DEBUG < INFO < NOTICE < WARNING < ERROR < CRITICAL < ALERT < EMERGENCY
  |                                           |
  +--- debug.log captures these              +--- exception.log captures these
```

### 6.5 Custom Logging (Architectural Pattern)

```php
<?php
// Inject \Psr\Log\LoggerInterface — NOT \Magento\Framework\Logger\Monolog directly
// This follows PSR-3 and allows swapping the logging backend

namespace Vendor\Module\Model;

use Psr\Log\LoggerInterface;

class MyService
{
    public function __construct(
        private readonly LoggerInterface $logger
    ) {}

    public function doSomething(): void
    {
        try {
            // business logic
        } catch (\Exception $e) {
            // Log to system.log with context
            $this->logger->critical($e->getMessage(), ['exception' => $e]);
        }
    }
}
```

> **Exam focus:** Always inject `\Psr\Log\LoggerInterface`, not the concrete Monolog class. This is the architecturally correct pattern — it decouples your module from the logging implementation.

## 7. Common Failure Patterns & Diagnosis

### 7.1 White Screen of Death (WSOD)

```
Symptom: Blank page or generic error page
         No visible error

Diagnosis Flow:
  Step 1 --> check var/log/exception.log  (ALWAYS FIRST)
  Step 2 --> check var/log/system.log
  Step 3 --> check var/report/<id> if an error ID is shown
  Step 4 --> switch to developer mode (if safe) for in-browser trace
  Step 5 --> check PHP error log (/var/log/php-fpm/error.log or similar)

NOT Step 1: clearing cache (destroys evidence, may not fix root cause)
NOT Step 1: running setup:di:compile (masks the real issue)
```

**Common WSOD causes and their log signatures:**

```
exception.log signature: "Circular dependency..."
-> Cause: Circular DI — two classes inject each other (directly or transitively)
-> Fix: Inject a factory or proxy instead of the concrete class

exception.log signature: "Class ... does not exist"
-> Cause: Missing generated/ files after code changes
-> Fix: bin/magento setup:di:compile

exception.log signature: "Plugin class ... does not implement..."
-> Cause: Wrong plugin method signature / return type
-> Fix: Correct the plugin method signature

exception.log signature: "Unable to unserialize value"
-> Cause: Stale cache with old serialized data after schema/model change
-> Fix: bin/magento cache:flush
```

### 7.2 Circular Dependency (DI)

```
Class A                    Class B
+-------------+            +-------------+
| __construct |            | __construct |
| (B $b)      |<---------- | (A $a)      |
+-------------+            +-------------+
      |                           |
      +---> needs B to exist      +---> needs A to exist
            but B needs A               but A needs B
            --> DEADLOCK (Circular DI)
```

**Solution pattern — use a Proxy:**

```php
<?php
// WRONG — direct injection creating circular dependency
public function __construct(
    private readonly \Vendor\Module\Model\ServiceB $serviceB
) {}

// CORRECT — inject proxy, which defers instantiation
public function __construct(
    private readonly \Vendor\Module\Model\ServiceB\Proxy $serviceB
) {}
```

> **Exam focus:** Magento can auto-generate proxies for you, but you must declare the `\Proxy` suffix in your constructor. The architectural reason for proxies is **lazy instantiation** — the real object is only created when a method is first called, breaking the circular dependency chain.

### 7.3 Missing generated/ Directory

After pulling code changes, adding plugins, or modifying di.xml:

```bash
# Symptom: "Class Vendor\Module\Model\Something\Interceptor does not exist"
# Cause: Interceptors (plugins), factories, and proxies live in generated/

# Fix sequence:
rm -rf generated/
bin/magento setup:di:compile

# In developer mode, generated/ is rebuilt automatically per-request
# In production mode, it MUST be pre-compiled
```

> **Exam focus:** `generated/` contains **interceptors** (plugin wrappers), **factories**, **proxies**, and **extension attribute interfaces** (e.g., `generated/code/Magento/Sales/Api/Data/OrderExtensionInterface.php`). It is build-time output — it should be in `.gitignore` and regenerated as part of every deployment.

### 7.4 Stale Cache

```bash
# Specific cache types
bin/magento cache:clean config     # Clean config cache only
bin/magento cache:clean full_page  # Clean full page cache only

# All cache types — clean (removes invalid) vs flush (removes everything including non-Magento)
bin/magento cache:clean   # Preferred — only removes Magento-tagged cache
bin/magento cache:flush   # Nuclear — removes everything in cache storage
```

| Command | What it does | When to use |
|---|---|---|
| `cache:clean` | Removes only Magento-managed cache entries | After config changes |
| `cache:flush` | Empties the entire cache storage backend | When cache storage is corrupted |
| `cache:disable <type>` | Disables a cache type (performance impact) | Debugging only |

### 7.5 Cron Not Running

```bash
# Check if cron is configured (non-Cloud environments)
crontab -l | grep magento

# Expected entry:
# * * * * * php /path/to/magento cron:run 2>&1 | grep -v "Ran jobs by schedule"

# Manually trigger cron (debugging only)
bin/magento cron:run

# Run only the indexer cron group
bin/magento cron:run --group=index

# Check for stuck cron jobs
SELECT * FROM cron_schedule WHERE status = 'running' AND executed_at < NOW() - INTERVAL 1 HOUR;
```

**Note:** There is no `bin/magento cron:status` command. The available cron CLI commands are `cron:run` (with optional `--group` flag), `cron:install`, and `cron:remove`. To check cron job status, query the `cron_schedule` table directly.

**Symptoms of cron not running:**
- Indexers showing "Reindex required" indefinitely
- Newsletters not sending
- Price rules not applying
- Session cleanup not happening → disk fills up

> **Exam focus:** `cron:run --group=index` runs only indexer-group jobs (group `id="index"` in `module-indexer/etc/cron_groups.xml`). On Cloud, cron is configured in `.magento.app.yaml`, not the OS crontab.

## 8. The Correct Upgrade / Deploy Order

This sequence is tested repeatedly. The order is not arbitrary — each step creates prerequisites for the next.

### 8.1 The Correct Sequence

```
Step 1: setup:upgrade
   |
   | Creates/updates DB schema and data.
   | Registers new modules, runs upgrade scripts.
   | MUST happen before di:compile because new classes
   | may be referenced in DI config.
   v
Step 2: setup:di:compile
   |
   | Scans all di.xml files, generates interceptors,
   | factories, proxies. Validates DI configuration.
   | MUST happen before SCD because SCD may need
   | generated classes for less/sass compilation plugins.
   v
Step 3: setup:static-content:deploy
   |
   | Copies/compiles static assets (CSS, JS, images)
   | to pub/static/. In production, assets must be
   | pre-deployed because they are NOT generated on-the-fly.
   v
Step 4: cache:flush
   |
   | Clears stale cached config, layout, block HTML.
   | Done LAST — clearing before deploy would just result
   | in cache being rebuilt with old data.
   v
   Deployment complete
```

### 8.2 Commands Reference

```bash
# Full production deployment sequence
bin/magento maintenance:enable

bin/magento setup:upgrade --keep-generated

bin/magento setup:di:compile

bin/magento setup:static-content:deploy -f \
    en_US en_GB \
    --area frontend \
    --area adminhtml

bin/magento cache:flush

bin/magento maintenance:disable
```

> **Exam focus:** The `--keep-generated` flag on `setup:upgrade` prevents deletion of the `generated/` directory, which avoids a window of downtime in production. Without it, Magento deletes `generated/` before running the upgrade, causing a brief period where interceptors don't exist.

### 8.3 Why the Order Matters (Architectural Reasoning)

| If you do X before Y | What breaks |
|---|---|
| `di:compile` before `setup:upgrade` | Compiled DI references classes from new modules that don't exist in DB yet — runtime mismatch |
| `static:deploy` before `di:compile` | LESS/SCSS compilation plugins (which are DI-based) haven't been compiled yet — CSS may fail |
| `cache:flush` before `static:deploy` | Cache is rebuilt from old static files — then flushed again on next request. Wasted work, not harmful, but architecturally sloppy |
| Skip `setup:upgrade` entirely | DB schema out of sync with code — data corruption, missing tables |

## 9. Hands-On: Breaking & Diagnosing a Plugin

### 9.1 The Setup — Create a Broken Plugin

```xml
<!-- Vendor/Sandbox/etc/di.xml -->
<?xml version="1.0"?>
<config xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
        xsi:noNamespaceSchemaLocation="urn:magento:framework:ObjectManager/etc/config.xsd">
    <type name="Magento\Catalog\Model\Product">
        <plugin name="sandbox_product_name_plugin"
                type="Vendor\Sandbox\Plugin\ProductNamePlugin"
                sortOrder="10"
                disabled="false"/>
    </type>
</config>
```

```php
<?php
// Vendor/Sandbox/Plugin/ProductNamePlugin.php
// THIS IS INTENTIONALLY BROKEN — wrong return type

namespace Vendor\Sandbox\Plugin;

use Magento\Catalog\Model\Product;

class ProductNamePlugin
{
    /**
     * BROKEN: after-plugin for getName() must return ?string (or string)
     * We're returning bool — this will cause a TypeError at runtime
     */
    public function afterGetName(Product $subject, $result): bool  // <-- WRONG TYPE
    {
        return true;  // <-- Wrong: should return a string (the product name)
    }
}
```

### 9.2 What Happens at Runtime

1. A page loads that calls `$product->getName()`
2. Magento's ObjectManager instantiates `ProductNamePlugin\Interceptor` (generated class)
3. The interceptor calls `afterGetName()`, which returns `true` (a bool)
4. The calling code receives `true` where it expected a string
5. Depending on PHP strict types: **TypeError** thrown → **exception.log** entry → **WSOD** in production

### 9.3 Diagnosing Using Logs

```bash
# Step 1: Check exception.log FIRST
tail -n 50 var/log/exception.log
```

**Expected log output:**

```
[2024-04-30 10:23:41] main.CRITICAL:
  TypeError: Return value of Vendor\Sandbox\Plugin\ProductNamePlugin::afterGetName()
  must be of type string, bool returned
  in /var/www/html/vendor/magento/framework/Interception/Interceptor.php:135
  Stack trace:
  #0 generated/code/Magento/Catalog/Model/Product/Interceptor.php(123): ...
  #1 Magento/Catalog/Block/Product/ListProduct.php(89): ...
  {"exception":"[object] (TypeError(code: 0): ...)"} []
```

```bash
# Step 2: Trace the generated interceptor to understand the call chain
cat generated/code/Magento/Catalog/Model/Product/Interceptor.php | grep -A 20 "getName"
```

**Generated interceptor snippet (for understanding):**

```php
<?php
// generated/code/Magento/Catalog/Model/Product/Interceptor.php
// Auto-generated — DO NOT EDIT DIRECTLY

public function getName(): ?string
{
    $pluginInfo = $this->pluginList->getNext($this->subjectType, 'getName');
    if (!$pluginInfo) {
        return parent::getName();
    } else {
        return $this->___callPlugins('getName', func_get_args(), $pluginInfo);
    }
}
```

The interceptor enforces the **original method's return type** (`?string`). When your plugin returns `bool`, PHP 7.4+ strict type enforcement triggers the TypeError.

### 9.4 Diagnosing Circular DI — Log Pattern

```bash
# Intentionally create circular dependency then run:
bin/magento setup:di:compile
```

```
[Magento\Framework\Exception\RuntimeException]
Circular dependency: Vendor\Sandbox\Model\ServiceA
depends on Vendor\Sandbox\Model\ServiceB,
and Vendor\Sandbox\Model\ServiceB depends on Vendor\Sandbox\Model\ServiceA.
```

> This error appears during **compile time** (di:compile), not at runtime — which is why di:compile is so important in CI/CD pipelines. It catches these issues before deployment.

### 9.5 The Fix

```php
<?php
// Vendor/Sandbox/Plugin/ProductNamePlugin.php — FIXED

namespace Vendor\Sandbox\Plugin;

use Magento\Catalog\Model\Product;

class ProductNamePlugin
{
    /**
     * Correct after-plugin: return type must match (or be compatible with)
     * the intercepted method's return type.
     * Product::getName() returns ?string, so we must return ?string.
     */
    public function afterGetName(Product $subject, ?string $result): ?string
    {
        if ($result === null) {
            return $result;
        }
        return strtoupper($result);  // Correct: returns a string
    }
}
```

```bash
# After fixing the plugin:
rm -rf generated/
bin/magento setup:di:compile
bin/magento cache:flush
```

### 9.6 Plugin Method Signature Rules (Reference)

```php
<?php
// BEFORE plugin — runs before the method, can modify arguments
public function beforeMethodName(
    SubjectClass $subject,
    $arg1,         // original method arguments
    $arg2          // ...
): array           // Return: array of modified arguments, or null
{}

// AFTER plugin — runs after the method, receives result
public function afterMethodName(
    SubjectClass $subject,
    $result,       // return value of original method
    $arg1,         // original method arguments (PHP 7+)
    $arg2          // ...
): <return_type>   // MUST match or be compatible with original return type
{}

// AROUND plugin — wraps the method entirely
public function aroundMethodName(
    SubjectClass $subject,
    callable $proceed, // call $proceed(...$args) to invoke original
    $arg1,
    $arg2
): <return_type>
{}
```

> **Exam focus:** The most common plugin error is an **after-plugin returning the wrong type**. The return type of `afterX()` must be compatible with the intercepted method's declared return type. If the original method returns `?string`, your after-plugin must also return `?string` — returning `void`, `bool`, or `int` will cause a TypeError.

## 10. Architect-Level Decision Frameworks

### 10.1 "Where should this config live?" Decision Tree

```
Is it a secret (API key, password, token)?
  YES --> env.php / OS environment variable ONLY
  NO
    |
    Is it environment-specific (differs per environment: staging vs prod)?
      YES --> env.php or CONFIG__* env var (NOT config.php)
      NO
        |
        Should it be configurable by a merchant (non-developer)?
          YES --> Admin UI (lands in core_config_data)
                  OR config.php if it should be locked across envs
          NO --> config.xml (module default) or config.php (committed)
```

### 10.2 "Why is the Admin field locked?" — The Full Architectural Answer

The exam may present a scenario question like:

*"A merchant reports that they cannot edit the store email address in Admin UI. They have not changed any code. What is the most likely cause and what is the architecturally correct resolution?"*

**Correct answer structure:**
1. **Cause:** `app:config:dump` was run and the value was written to `config.php`. Config values in `config.php` take precedence over `core_config_data` and the Admin UI field is locked to prevent drift.
2. **Resolution options (ranked by architectural correctness):**
   - **Best:** Set an env var override (`CONFIG__DEFAULT__TRANS_EMAIL__IDENT_GENERAL__EMAIL`) — preserves config.php integrity, overrides for this environment only
   - **Acceptable:** Remove the specific key from `config.php` — restores editability but must be done on all environments
   - **Avoid:** Directly editing `core_config_data` via SQL — bypasses the config system, will be overridden by `config.php` anyway

### 10.3 Mode Selection — Architectural Criteria

| Criterion | developer | production |
|---|---|---|
| Is this a live customer-facing environment? | No | **Yes** |
| Do you need to see errors in-browser? | Yes | No |
| Will CSS/JS change frequently? | Yes (symlinked, instant) | No (deploy pipeline) |
| Is performance critical? | No | **Yes** |
| Are there CI/CD pipelines for asset compilation? | Optional | **Required** |

> **Exam focus:** Running `developer` mode in production is not just a performance issue — it is a **security vulnerability** (stack traces expose file paths, class names, and potentially sensitive data). An architect must be able to articulate both the performance *and* security reasons.

### 10.4 Log-First Debugging — The Architectural Principle

The reason exception.log must be checked **before** any remediation action:

```
Clear cache first approach (WRONG):
  Problem -> Clear cache -> May fix symptom -> Root cause unknown
                                             -> Problem recurs
                                             -> Evidence destroyed

Log-first approach (CORRECT):
  Problem -> Read exception.log -> Understand root cause -> Fix root cause
                                                         -> Verify in logs
                                                         -> Problem does not recur
```

On the exam, if a scenario offers "check logs" and "clear cache" as possible first steps — **check logs is always architecturally correct first step**.

## Quick-Reference Checklist

### Configuration Files
- [ ] `config.php` — committed to VCS, contains module list + shared system config
- [ ] `env.php` — **never** committed, contains DB, cache, crypt key, MAGE_MODE
- [ ] `config.php` is written by `app:config:dump`; `env.php` is written by the installer or manually
- [ ] After `app:config:dump`, Admin UI fields for dumped values are **locked/greyed out**
- [ ] Sensitive config (passwords, API keys) must go in `env.php` / OS env vars — **never** `config.php`

### Configuration Hierarchy (Low → High priority)
- [ ] Layer 1: `config.xml` (module defaults)
- [ ] Layer 2: `core_config_data` (Admin UI / database)
- [ ] Layer 3: Environment variables (highest priority — always wins)
- [ ] Env var format: `CONFIG__DEFAULT__SECTION__GROUP__FIELD`

### Sensitive Config Declaration
- [ ] Sensitive paths declared via `di.xml` → `Magento\Config\Model\Config\TypePool` injection (`argument name="sensitive"`, path → "1")
- [ ] **No `config_sensitive.xml` file type exists** in Magento
- [ ] `bin/magento config:sensitive:set <path> <value>` writes value to `env.php`, bypassing `config.php`

### Admin UI Lock Behaviour
- [ ] Values in `config.php` lock the corresponding Admin UI field
- [ ] To override: use `CONFIG__*` env var OR edit `config.php` directly
- [ ] To restore Admin UI editability: remove the key from `config.php`

### Application Modes
- [ ] `developer` — errors shown in browser, assets on-the-fly, DI rebuilt per-request
- [ ] `production` — errors suppressed to logs, assets must be pre-deployed, DI must be pre-compiled
- [ ] `default` — do not use in either dev or prod environments
- [ ] Running developer mode in production = security + performance risk

### Log Files
- [ ] `exception.log` — all uncaught exceptions with stack traces (**check FIRST for WSOD**)
- [ ] `system.log` — notices, warnings, non-critical application messages
- [ ] `debug.log` — verbose debug output; **must be disabled in production**
- [ ] `cloud.log` — Adobe Commerce Cloud platform/hook events
- [ ] `deploy.log` — deployment phase output (di:compile, SCD, config import)
- [ ] `var/report/<id>` — full exception reports linked from error pages

### Debug Logging
- [ ] `dev/debug/debug_logging` is a **deployment config** path stored in `env.php` — not a system config
- [ ] Disable via: `bin/magento setup:config:set --enable-debug-logging=0`
- [ ] Auto-disabled when switching to production mode (`deploy:mode:set production`)

### White Screen of Death (WSOD)
- [ ] **FIRST step: check `var/log/exception.log`** — not clearing cache
- [ ] Common causes: circular DI, missing generated/, wrong plugin return type, stale cache
- [ ] Circular DI signature in log: "Circular dependency: ClassA depends on ClassB..."
- [ ] Missing generated/ signature: "Class ...Interceptor does not exist"
- [ ] Wrong plugin type signature: "TypeError: Return value of ...afterX() must be..."

### Correct Upgrade / Deploy Order
- [ ] 1. `setup:upgrade` — sync DB schema with code
- [ ] 2. `setup:di:compile` — generate interceptors, factories, proxies
- [ ] 3. `setup:static-content:deploy` — pre-deploy assets for production
- [ ] 4. `cache:flush` — clear stale cached data
- [ ] `--keep-generated` flag on `setup:upgrade` prevents downtime window in production
- [ ] `cache:clean` = remove Magento-tagged entries; `cache:flush` = nuke entire cache storage

### Plugin Rules
- [ ] `before` plugin: return array of modified args or null
- [ ] `after` plugin: **must return type compatible with original method's return type**
- [ ] `around` plugin: must call `$proceed()` and return compatible type
- [ ] Generated interceptors live in `generated/` — never commit, always regenerate on deploy

### Circular Dependency Resolution
- [ ] Inject `\Vendor\Module\Model\ClassName\Proxy` instead of the class directly
- [ ] Proxy defers object instantiation until first method call (lazy loading)
- [ ] Circular DI is detected at **compile time** by `setup:di:compile`

### Cron
- [ ] Cron commands: `cron:run`, `cron:run --group=<group>`, `cron:install`, `cron:remove`
- [ ] **No `cron:status` command exists** — check `cron_schedule` table for job status instead
- [ ] Indexer cron group name is `index` (declared in `module-indexer/etc/cron_groups.xml`)
- [ ] On Cloud: configured in `.magento.app.yaml`, not OS crontab
- [ ] Stuck jobs in `cron_schedule` table can block subsequent runs

### Architect-Level Reasoning (Exam Differentiators)
- [ ] Config.php lock = intentional, for environment parity and drift prevention
- [ ] Log-first debugging = preserves evidence, identifies root cause vs. symptom
- [ ] `env.php` for secrets = PCI/security compliance, not just convention
- [ ] Proxy pattern for DI = lazy instantiation to break circular dependencies
- [ ] `developer` mode in production = security vulnerability (exposes internals), not just slow
- [ ] Always inject `Psr\Log\LoggerInterface`, not concrete Monolog class (PSR-3 compliance)
- [ ] `cache:clean` preferred over `cache:flush` in most cases — less destructive
