- [ ] Day 3 — Events & Observers Architecture (2026-04-13) [60min]

- [ ] Day 4 — Request Flow, Routing & Controller Design (2026-04-14) [90min]

## Week 2 — Customization, Integration & Code Review

- [ ] Day 8 — Advanced Plugin Patterns & Interceptor Pitfalls (2026-04-20) [90min]
  > Go deeper on plugins — the architect exam loves edge cases here:  • **Plugin on interface vs abstract class**: plugins attach to the concrete class in the DI container. If preference points to a different class, plugins on the original interface may not fire as expected. • **Around plugin misuse**: around plugins that don't call $proceed break the chain — this is a critical design anti-pattern. Know when around plugins are justified (wrapping with try/catch, conditional skipping). • **Plugin sorting with multiple modules**: when two modules define plugins on the same method with same sortOrder, alphabetical module name breaks the tie — know this tiebreaker rule • **Plugin on Repository methods**: common pattern in EE for B2B features — study how Magento\Company adds plugins on CustomerRepository • **Generated code pitfalls**: if you modify a plugin after di:compile, you MUST recompile or clear generated/code — in production this means a deployment step • **Hands-on**: Create a scenario with 3 plugins (before/around/after) on the same method, log execution order, then add a 4th plugin from a 'second module' to verify sort order behavior • **Exam trap**: An `after` plugin receives the RESULT of the method (or the result of the last `around` plugin) — not the original arguments. Many candidates get the method signature wrong.
- [ ] Day 8 — Code Review Standards & MEQP (2026-04-20) [60min]
  > Section 2 focus — reviewing and enforcing code quality:  • **Magento Extension Quality Program (MEQP)**: What it checks, PHP_CodeSniffer with Magento standards, how to run `phpcs --standard=Magento2` on a module • **Common violations to recognize**: direct ObjectManager usage (anti-pattern), SQL in models instead of ResourceModel, hardcoded URLs, missing @api annotations on service contracts • **SOLID principles in Commerce context**: how DI enforces SRP, how service contracts support OCP, how plugins support LSP without class replacement • **Tricky angle**: Using ObjectManager directly is NOT always wrong in Magento — it's acceptable in factory classes, tests, and CLI commands (with caveats). The exam may present a scenario where it's actually justified. • **Code smell patterns**: Business logic in templates (should be in Block/ViewModel), session usage in models (wrong layer), direct SQL queries bypassing ORM • **Review checklist**: Create a mental checklist an architect would use when reviewing a PR for a Commerce module
- [ ] Day 9 — Staging & Preview (EE) + B2B Architecture (2026-04-21) [90min]
  > EE-exclusive features are heavily tested at architect level — these differentiate expert from architect:  • **Content Staging architecture**: version tables (sequence tables), EntityManagerInterface, staging plugins on save/delete operations, how scheduled updates work in the database • **Staging pitfalls**: Staging changes the entity_id concept — products have a row_id (auto-increment) AND entity_id. Queries joining on entity_id behave differently in EE vs CE. This is a notorious expert trap. • **Staging preview**: how the preview functionality uses a timestamp parameter to load a specific version — the URL hash mechanism • **B2B module architecture**: Company hierarchy, shared catalogs (price overrides per catalog), negotiable quotes (quote modification flow), requisition lists, quick order • **SharedCatalog**: how it overrides tier prices and category assignments — uses its own price indexer and category permission system • **Tricky angle**: In EE with B2B, the catalog price rules and shared catalog prices interact in a specific priority order. Know which takes precedence. • **Hands-on**: On your EE local, create a scheduled update for a product, then query the staging_update and catalog_product_entity tables to see how versioning is stored
- [ ] Day 9 — MSI (Multi-Source Inventory) Architecture (2026-04-21) [60min]
  > MSI is a major architectural addition and exam topic:  • **MSI table structure**: inventory_source, inventory_source_item, inventory_reservation, inventory_stock, inventory_stock_sales_channel • **Salability check flow**: how `IsProductSalableInterface` replaces the legacy `isSalable()` — the new chain of conditions • **Reservations**: append-only log pattern (never update, only insert) — why this design was chosen (concurrency, audit trail) • **Source selection algorithms**: Priority, Distance — how they determine which source to ship from • **Tricky angle**: MSI uses a reservation system instead of direct quantity updates. When an order is placed, a negative reservation is appended. This means `qty` in inventory_source_item doesn't reflect actual available quantity without summing reservations. • **SSA (Source Selection Algorithm)**: custom SSA implementation — SourceSelectionServiceInterface • **Legacy stock vs MSI**: `cataloginventory_stock_item` is still written to for backward compatibility — why this matters for custom code • **Hands-on**: Create a multi-source scenario in your local, place an order, and inspect the inventory_reservation table to see the reservation pattern
- [ ] Day 10 — Indexing Architecture & Index Management (2026-04-22) [60min]
  > Indexers are critical for performance design decisions:  • **Indexer types**: Full reindex vs partial (mview-based delta indexing) — how MView triggers work at the database level (MySQL triggers on source tables) • **indexer.xml**: declarative indexer registration, dependencies between indexers, shared index • **MView**: mview.xml — subscriptions (which tables trigger delta), the mview changelog table pattern • **Index modes**: Update on Save vs Update by Schedule — architect must know the tradeoffs (UoS: immediate, blocks save; UbS: eventual consistency, better performance) • **Tricky angle**: In Update by Schedule mode, a product's price change is NOT immediately reflected in search results — it waits for the next indexer run. This is a design decision with UX implications the exam may probe. • **Custom indexer**: implementing IndexerInterface, integrating with MView for delta indexing • **EE**: Additional indexers in EE (SharedCatalog price indexer, CMS Staging indexer) — know they exist and their purpose • **2.4.8 note**: Verify current indexer performance improvements and any new indexers added in recent versions
- [ ] Day 10 — Message Queue Architecture (RabbitMQ/DB Queue) (2026-04-22) [90min]
  > Asynchronous processing is a key architect topic for scalability:  • **Queue topology**: communication.xml (topics, queues, bindings, exchanges), consumer configuration, publisher configuration • **Queue types**: DB queue (default, uses queue_message table) vs RabbitMQ — when to choose each • **Consumer types**: synchronous consumer, asynchronous consumer, batch consumer — differences in implementation • **Publisher → Topic → Queue → Consumer flow**: know how a message travels end-to-end, including serialization (JSON) • **Tricky angle**: DB queue consumers run via cron by default. RabbitMQ consumers are long-running processes. In Cloud, consumers are managed by supervisord. Mixing these mental models causes confusion in exam scenarios. • **Error handling in queues**: rejected messages, dead letter queues (RabbitMQ), retry logic • **Async API integration**: how /async/V1/ endpoints publish to queues and how bulk consumers process them • **Hands-on**: Define a custom topic and queue in communication.xml, publish a message programmatically, run the consumer with `bin/magento queue:consumers:start your_consumer` • **Cloud consideration**: In Adobe Commerce Cloud, queue consumer configuration in `.magento.env.yaml` under `CRON_CONSUMERS_RUNNER`
- [ ] Day 11 — Caching Architecture & Cache Types (2026-04-23) [90min]
  > Caching strategy is a pillar of Commerce architecture:  • **Cache types**: config, layout, block_html, collections, reflection, db_ddl, compiled_config, eav, customer_notification, config_integration, config_integration_api, full_page, config_webservice, translate — know each type and what invalidates it • **Cache backends**: File (default), Redis (recommended for production), Varnish (for FPC) • **Redis architecture for Commerce**: cache + session as separate Redis instances, Redis Cluster vs Sentinel, the L2 cache (Redis + local memory) introduced in 2.4.x • **Varnish integration**: how ESI (Edge Side Includes) works for blocks with different cache lifetimes, Varnish VCL customization, X-Magento-Tags header for cache invalidation by tags • **Block cache tags**: identities() method returning cache tags, how CacheContext collects tags and adds them to the response headers • **Tricky angle**: `full_page` cache is stored in Varnish (or built-in FPC). When a product price changes, the product's cache tags are used to purge all cached pages containing that product. If identities() doesn't return the right tags, pages won't be invalidated correctly — a critical bug architects must catch in code review. • **Hands-on**: Enable Varnish on local (or use built-in FPC), modify a product price, and inspect which cache entries are purged via X-Magento-Tags and cache_invalidate events
- [ ] Day 11 — Search Architecture (Elasticsearch/OpenSearch) (2026-04-23) [60min]
  > Search is a core scalability and architecture topic:  • **Search engine evolution**: MySQL fulltext (legacy) → Elasticsearch → OpenSearch (current recommended in 2.4.8) • **Index mapping**: how Commerce maps product attributes to ES/OS fields (keyword vs text vs numeric) • **Search adapter architecture**: SearchAdapterInterface, how the search query is built and translated to ES/OS query DSL • **Layered navigation**: how aggregations work, custom filterable attributes, price buckets • **Tricky angle**: In 2.4.8, MySQL as a search engine is deprecated for catalog search. If FPC hit rate is low, no amount of PHP/MySQL tuning will compensate. Architects must diagnose WHY FPC is missing (user-specific content, uncacheable blocks). • **Uncacheable blocks**: `cacheable="false"` on any block in a layout makes the entire PAGE uncacheable — this is a critical design constraint • **Hands-on**: Add `cacheable="false"` to a block on your local, observe in the response headers that X-Magento-Cache-Control becomes private
- [ ] Day 14 — Commerce Test Frameworks (Unit, Integration, Functional) (2026-04-27) [60min]

Using the real DI container means they're slower but more realistic.
